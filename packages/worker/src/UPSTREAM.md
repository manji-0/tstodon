# Upstream: Mastodon web frontend

This directory is Mastodon's web frontend (upstream's `app/javascript`: the React app, its styles, images and fonts), vendored so tstodon can change it directly. It is the client of the Void app in `packages/worker` (Void's "SPA + API" shape: frontend in `src/`, server conventions in `app/`, shared server code in `server/`), built by the same `vite build` as the Worker. Mastodon is AGPL-3.0-or-later, as tstodon is; see `LICENSE` and `AUTHORS.md`.

## Fetched at build time

`public/emoji/` (twemoji SVGs, about 21 MB) and `public/ocr/` (Tesseract language data, about 11 MB) are not committed (`fetched` in `upstream.json`). The Void build (the `tstodon:upstream-assets` plugin's `config` hook, so `vp dev`, `vp build`, `void deploy` and CI all run it) and `packages/worker/vitest.config.ts` fetch them from the commit above into `.cache/mastodon-web/upstream/<commit>/`, checking that the tag still points at that commit, and link each `served` one into `packages/worker/public/` (gitignored there). The Worker serves `emoji/`; `ocr/` is fetched so the tree matches upstream but is not served (as before vendoring).

## Local changes

Changes against upstream, so a future merge knows what is ours:

- The frontend moved from upstream's `app/javascript/` to `packages/worker/src/`, so two `import.meta.glob` / dynamic import paths that climb to the repository's `node_modules` lost one `../`: `mastodon/polyfills/intl.ts` (`@formatjs/intl-pluralrules/locale-data`) and `mastodon/features/emoji/loader.ts` (`emojibase-data`). Without that the globs match nothing and the build silently drops the plural-rules locale data and the emoji picker's data. (`testing/api.ts` has the same pattern but is Storybook-only and already pointed above upstream's root.)
- `src/package.json` (`{ "private": true }`): the nearest `package.json` of the frontend has no `type`, as upstream's has none. Under `packages/worker`'s `"type": "module"`, Rolldown reads a default import of a CommonJS module with Node's semantics (`module.exports`, not its `__esModule` `default`), which breaks `import LoadingBar from 'react-redux-loading-bar'`; with `"type": "commonjs"` it wraps the side-effect-only `inline/theme-selection.js` as a CommonJS module, which the shell's classic `<script>` cannot load.
- `config/formatjs-formatter.js` is `config/formatjs-formatter.cjs` (CommonJS under `packages/worker`'s `"type": "module"`) and reads `../src/mastodon/locales/en.json`.
- `vite.config.mts` (ported to `web-build.ts`): the client is Vite's `client` environment of the Void app. Vite's root is `packages/worker`, not `app/javascript`, and `base` is `/`; the output keeps upstream's URLs by naming files under `packs/` (`build.assetsDir: "packs"`, chunk, entry and asset file names prefixed `packs/`, also for the emoji Web Worker's bundle), except the service worker, which is emitted as `/sw.js` (upstream links `public/sw.js` to `packs/sw.js`). Upstream's plugins run unmodified, scoped to the client environment; the ones that take Vite's root for `app/javascript` (`plugin-assets-manifest`, `plugin-sw-locales`) get `src/` as root, and the themes plugin's `config` hook is called directly for the `themes/*` entries. Dropped: source maps (the Worker's assets never shipped them), `rollup-plugin-gzip` (Workers compress responses), `vite-plugin-manifest-sri` (the Worker renders no `integrity`), `rollup-plugin-visualizer`, the dev server's port and proxy settings (Void's dev server serves everything) and the themes plugin's `/packs-dev/themes/` dev rewrite (the dev shell links the theme's source). The Vite and Vitest are the workspace's (Vite+ core 1.3.0, i.e. Vite 8.3; Vitest 5), not upstream's 8.2 / 4.1.
- `vitest.config.mts` (ported to `packages/worker/vitest.config.ts`): only upstream's `legacy-tests` project (jsdom), as the `web` project, run from `packages/worker` (`pnpm test:web`); the Storybook project is gone.
- `tsconfig.json` (ported to `src/tsconfig.json`): `paths` relative to `src/`, no `incremental` cache, and the Storybook files (`*.stories.*`, `testing/api.ts`, `mastodon/components/status/testing.ts`) excluded. The typecheck runs on the workspace's TypeScript 7 (`pnpm typecheck:web`), not upstream's TypeScript 6.
- Storybook, ESLint, Stylelint and oxfmt are not set up: their configs and packages were removed (the story files stay, unbuilt and unchecked, so merges stay mechanical). Root `vp check` skips `src/` and `config/` (upstream's formatting and lint).
- `package.json` (merged into `packages/worker/package.json`): upstream's dependency versions. Removed with the tooling above: `@csstools/stylelint-formatter-github`, `cross-env`, `rollup-plugin-gzip`, `rollup-plugin-visualizer`, `vite-plugin-manifest-sri`, ESLint and its plugins, `typescript-eslint`, `globals`, Stylelint and its config, `oxfmt`, Storybook and its addons, `chromatic`, `msw`, `msw-storybook-addon`, `@vitest/browser`, `@vitest/browser-playwright`, `@vitest/coverage-v8`, `@vitest/ui`, `playwright`, `typescript` (TS 6) and `@typescript/native`; `vite` and `vitest` come from the workspace catalog. Upstream relies on Yarn hoisting for a few packages it does not declare; pnpm does not hoist, so they are declared at the versions upstream's `yarn.lock` resolved: `browserslist` (read by the build), `tesseract.js-core` (imported by the alt text modal), and for the typecheck and tests `@types/history`, `jsdom` and `redux` (`HOISTED` in `scripts/import-mastodon-web-lock.mjs`). Scripts: only `i18n:extract` is kept.
- `UPSTREAM.md`, `upstream.json`, `package.json` added here.
- Repository root: `pnpm-workspace.yaml` lists the install scripts the frontend's dependencies may not run; `vite.config.ts` keeps `vp check` out of `src/` and `config/`.

### REST types from `@tstodon/api`

<!-- constrained-by ../../api/README.md -->

The REST JSON shapes the client reads are defined once, in `packages/api` (`@tstodon/api`), and the server's document builders return the same types.

- `mastodon/api_types/*.ts` keep their paths and exported names but re-export the entity types from `@tstodon/api` (`export type { ApiStatusJSON, ... } from '@tstodon/api'`, erased at build time). What stays local: client-only shapes and helpers (`ApiStatusTranslationJSON`, the client's translation with `contentHtml` / `spoilerHtml`; the collection envelopes and payloads; `ApiProfileUpdateParams`; `ValidationErrorResponse`; `allNotificationTypes`, the types this UI requests), and `isStatusVisibility` / `isQuotePolicy`, now built on `@tstodon/api/values` (Zod-free constants: importing it adds no Zod to the bundle), as is `reducers/compose.ts`'s visibility order (`STATUS_VISIBILITIES`). `notifications.ts` aliases `NotificationType`, `ApiNotificationJSON` and `ApiNotificationGroupJSON` to Mastodon's types only (`MastodonNotificationType`, `ApiMastodonNotification*`): tstodon's `move` notification is not one this UI renders.
- The shared types follow Mastodon's wire format, which is stricter than upstream's hand-written interfaces in places (nullable fields upstream typed optional or non-null). The code that read them was adjusted, each change type-level or a null fallback with the behaviour upstream had for a missing value: `models/status.ts` (`StatusShape`: `edited_at`, `language`, `in_reply_to_id`, `in_reply_to_account_id`, `card` and `application.website` may be `null`), `actions/importer/statuses.ts` (no dead `content` / `quote_approval` defaults under the spread; a `null` attachment description searches as empty), `components/status/attachments.tsx` (a `null` description, preview or blurhash, and `meta.original` / `meta.colors` an attachment may lack: no aspect ratio, no colours), `components/status/content.tsx`, `components/status/status.tsx` (a `null` language or reply id passed on as `undefined`), `components/blurhash.tsx` (`hash` may be `null`; it already drew nothing then), `components/poll.tsx` (an option's `votes_count` is `null` while a poll hides its totals: counted as 0), `reducers/contexts.ts`, `actions/compose_typed.ts` (no redirect to a `null` URL), `features/notifications_v2/components/notification_group_with_status.tsx` (`timestamp` optional: a group fetched on its own has no `latest_page_notification_at`, which it already handled), `models/notification_group.ts` (an `annual_report` notification keeps its report, as its group does) and `testing/factories.ts` (the fixtures fill the required fields).
- On a merge, upstream's changes to `app/javascript/mastodon/api_types/*.ts` are not taken as they are: apply each new or changed field to the matching schema in `packages/api/src/*.ts` (Mastodon's serializers are the reference), keep the files here as re-exports, and let `pnpm typecheck:web` and the Worker's typecheck show the client and server code that must follow. A new upstream-only helper stays in the `api_types` file.

### Initial state and streaming types from `@tstodon/api`

<!-- constrained-by ../../api/README.md -->

The initial state and the streaming events the Worker sends are typed in `@tstodon/api` too (`packages/api/src/initial-state.ts`, `streaming.ts`), imported type-only (the bundle stays free of Zod).

- `mastodon/initial_state.ts`: `InitialState` is `ApiInitialStateJSON`, and the local `InitialStateMeta` and `InitialStateLanguage` alias the shared types (upstream's hand-written `InitialStateMeta`, `IntialStateRole`, `InitialStateWrapstodon`, `InitialStateCompose` and `InitialState` interfaces are gone). The shared shape follows Mastodon's serializer where upstream's interfaces did not: `access_token`, `admin`, `sso_redirect` and `status_page_url` may be `null`, `show_trends` and `compose.text` are optional, `role.collection_limit` is optional (tstodon has no collections), and `display_media`, `emoji_style`, `default_privacy` and `default_quote_policy` are their literal unions. `getAccessToken()` turns a `null` token into `undefined`, as it returned for a missing one.
- `mastodon/stream.ts` (upstream's `stream.js`, now TypeScript, see "JS actions moved to TypeScript"): `StreamEvent` is `ApiStreamingWireEventJSON` (the event as received, an entity payload still a JSON string; upstream typed the payload `object`), a WebSocket message is an `ApiStreamingMessageJSON`, and an SSE frame is built into its event by name (`eventSourceEvent`) instead of being cast.
- `mastodon/actions/streaming.ts` (upstream's `streaming.js`): entity payloads go through a local `decode(event, payload)` (`JSON.parse`, typed with the payload type of that event), and a `notification` whose type is not Mastodon's (tstodon's `move`, `isMastodonNotificationType` from `@tstodon/api/values`) is dropped before the notification actions: the UI's REST requests leave that type out, and the stream's reached the legacy alert code with no message for it and the grouped list as an empty group. None of upstream's `@ts-expect-error` / `@ts-ignore`s in the two files is left.

### REST request params from `@tstodon/api`

<!-- constrained-by ../../api/README.md -->

The request wrappers in `mastodon/api/*.ts` type what they send with the params schemas' input types from `@tstodon/api` (`packages/api/src/params/`), which the Worker parses with, imported type-only (`import type`, or `satisfies` on an object literal), so the bundle still has no Zod.

- `api/accounts.ts`: `apiGetAccounts` (`ApiGetAccountsParams`), `apiSubmitAccountNote`, `apiFollowAccount` (its `params` are `ApiFollowAccountParams`: `reblogs`, `notify`, `languages`, all optional), `apiPostFeaturedTag`, and `apiGetFamiliarFollowers`, which sends `id` as Mastodon's documented `id[]` array (upstream sent a single `id`; both are accepted).
- `api/compose.ts` (`apiUpdateMedia`: `ApiUpdateMediaParams`), `api/directory.ts` (`apiGetDirectory`: `ApiGetDirectoryParams` without `limit`), `api/interactions.ts` (`apiReblog`), `api/polls.ts` (`apiPollVote`), `api/search.ts` (`apiGetSearch`: `ApiSearchParams` with `q` required and `type` an `ApiSearchType`), `api/suggestions.ts`, `api/tags.ts` (`apiGetFollowedTags`).
- `api/lists.ts`: `apiCreate` takes `ApiCreateListParams`; `apiUpdate` takes `ApiUpdateListParams` with the list's `id`, which now goes only in the path (upstream sent the whole list, `id` included, as the body). The member add / remove and member list send `ApiListAccountsParams` / `ApiGetListAccountsParams`. `actions/lists_typed.ts`'s `createList` / `updateList` take the same types instead of `Partial<List>`.
- `api/notifications.ts`: the list, grouped list and request list take `ApiGetNotificationsParams`, `ApiGetGroupedNotificationsParams` and `ApiGetNotificationRequestsParams`; the bulk accept / dismiss send `ApiNotificationRequestIdsParams`. `apiFetchNotificationGroups` lost upstream's `url` param, which no caller passed and which would have gone out as a `url=` query param.
- `api/notification_policies.ts`: `apiUpdateNotificationsPolicy` takes `ApiUpdateNotificationPolicyParams` instead of `Partial<NotificationPolicyJSON>` (which allowed sending `summary`).
- `api_types/profile.ts`: `ApiProfileUpdateParams` is `@tstodon/api`'s `ApiUpdateProfileParams` (re-exported under upstream's name) instead of a local `Pick` of `ApiProfileJSON`.
- Not changed, because the Worker has no route for them yet: `api/collections.ts`, `apiSubscribeByEmail`, `apiSetQuotePolicy` (`statuses.ts`) and `api/annual_report.ts`. No action is left in JavaScript (see "JS actions moved to TypeScript" below); the few TypeScript callers that use `api()` / `apiRequest` directly (`actions/markers.ts`, `hooks/useSearchAccounts.ts`, ...) stay untyped as upstream left them.

### Post length counting from `@tstodon/core/post-text`

The compose form counts a post's length with the Worker's own rule, `@tstodon/core/post-text` (Zod-free: it imports only its own files), so the counter and the server's 422 agree.

- `features/compose/util/url_regex.js` re-exports `postUrlRegex` as `urlRegex`: the same twitter-text pattern upstream composed here, now generated once into `packages/core/src/post-text-url-pattern.ts` (`scripts/generate-post-text-url-pattern.mjs`) and checked against twitter-text by `packages/core/src/post-text.test.ts`. `twitter-text` is no longer a dependency of `packages/worker` (it is a dev dependency of `packages/core`).
- `features/compose/util/counter.js` re-exports `countableText` and `graphemeLength`. `compose_form.jsx` counts with `graphemeLength` instead of `stringz`'s `length`, in `canSubmit` and through the `length` prop it passes to `features/compose/components/character_counter.tsx` (new and optional, `stringz`'s `length` by default). That is grapheme clusters, as Mastodon's `StatusLengthValidator` counts (code points where a browser lacks `Intl.Segmenter`). The alt text modal renders the same counter and still counts with `stringz`, as its own check does.
- On a merge, an upstream change to `counter.js` or `url_regex.js` goes into `packages/core/src/post-text.ts` (or the generator), not these files.

### Hashtags from `@tstodon/core/post-text`

The web UI decides what is a hashtag with the Worker's rule, Mastodon's `Tag::HASHTAG_RE` (`hasHashtag`, `isHashtagName` in `@tstodon/core/post-text`), so the compose form warns about the tags the server stores.

- `features/compose/components/warning.tsx`: the "not listed under any hashtag" warning tests `hasHashtag(text)` instead of upstream's `HASHTAG_PATTERN_REGEX`. Upstream's client pattern differed from its server's (`#` after any non-word character, `\p{N}` for digits, no `・`), so the warning could fire for `(#tag)`, which no hashtag lists.
- `features/compose/components/search.tsx`: the "go to hashtag" quick action takes `isHashtagName` instead of `HASHTAG_REGEX`.
- `utils/hashtags.ts`: `HASHTAG_PATTERN_REGEX`, `HASHTAG_REGEX`, their builders, `ALPHA` and `HASHTAG_SEPARATORS` are gone. `WORD` stays for the autosuggest.

### JS actions moved to TypeScript

<!-- constrained-by ../../api/README.md -->

Upstream's JavaScript Redux actions are moved to TypeScript in place (`git mv x.js x.ts`): every export, action type constant and dispatched action keeps its name and shape, since the reducers (mostly JavaScript) read them. Their HTTP goes through typed wrappers in `mastodon/api/*.ts`, with the shared response types and the params input types from `@tstodon/api` (type-only). On a merge, an upstream change to one of these `.js` files must be ported by hand into its `.ts` file here (the `.js` no longer exists, so git reports a modify/delete conflict).

- `actions/timelines.ts`: every timeline page goes through `apiFetchTimeline` (`api/timelines.ts`, typed with `ApiTimelineParams`, the union of `ApiGetHomeTimelineParams`, `ApiGetPublicTimelineParams`, `ApiGetTagTimelineParams`, `ApiGetListTimelineParams`, `ApiGetLinkTimelineParams` and `ApiGetAccountStatusesParams`); each `expand*` / `fill*Gaps` builds its params with its endpoint's type (`satisfies`). `expandTimeline` keeps upstream's `(timelineId, path, params)`, as `timelines_typed.ts` calls it with a path. - `actions/notifications.ts`: `updateNotifications` reads a status only on the types that carry one (a `null` status no longer throws), and shows a desktop notification only for a type with a title message: for `severed_relationships` or `annual_report` it threw (`IntlMessageFormat` of `undefined`), which also kept the streamed notification out of the grouped list. `requestBrowserPermission` takes a `(permission: NotificationPermission) => void`.

### JS reducers moved to TypeScript

<!-- constrained-by ../../api/README.md -->

Upstream's JavaScript reducers are moved to TypeScript in place (`git mv x.js x.ts`), with the same export `reducers/index.ts` imports, so their slices of `RootState` are typed. The state keeps its runtime shape: the same Immutable `Map`s, `List`s and `OrderedSet`s, keys and values (no `Record`s), since JavaScript components still read it with `.get` / `.getIn` / `.toJS`. One type describes a `Map` with a fixed set of fields: `ImmutableMapOf<Fields>` (`mastodon/utils/immutable_map_of.ts`, mirroring Immutable 5's `MapOf`, so moving to Immutable 5 is a rename), a type over a plain `Immutable.Map` whose `get` / `has` / `set` / `update` / `merge` / `withMutations` know each field's type, so readers call `.get('field')` with no getter or guard to narrow it; `get(key, notSetValue)` and `update(key, notSetValue, updater)` drop `undefined` from an optional field's type, the not-set value standing in for a missing field (the states leave an optional field out rather than set it to `undefined`). `immutableMapOf(fields)`, `immutableFromJS`, `immutableToJS` and `immutableMapWith(map, key, value)` (a `set` that retypes the field, as `makeGetStatus` puts a status's account in place of its id) are the only places these types meet Immutable 4's looser ones (`ImmutableMap(fields)`, `fromJS`, `toJS`, `set`, nothing more at runtime), and `PlainOf` / `ImmutableOf` name a shape's plain and Immutable forms (`ImmutableOf` turns a union of object types into one `ImmutableMapOf` of their merged fields, `MergedOf`, as a union of Maps cannot be read with `get`, and keeps an Immutable value as it is). An `ImmutableMapOf` is invariant in its fields (`set` and `update` take them); `ImmutableMapReaderOf<Fields>` is its reading half (`get`, `has`, `getIn`), which a Map whose fields are subtypes of `Fields` is, so a function that only reads takes Maps of several shapes. `getIn` / `setIn` stay `unknown`: TypeScript reads nested fields with chained `get`s. A map keyed by ids (statuses, timelines, filters, user lists, ...) stays an `ImmutableMap<string, X>` of such values. Plain-object actions are typed from their creators' `ReturnType`, or from an exported action type where a thunk dispatches the object itself (`TimelineUpdateAction`, `ComposeReplyAction`, ..., checked with `satisfies`), and their type constants are `as const` (`PlainActionOf` in `utils/types.ts` gives the literal type for `COMPOSE_LANGUAGE_CHANGE` and `FILTERS_IMPORT`, whose files other reducers own). Most reducers are RTK `createReducer`s: `addCase` for RTK action creators and for a plain constant with its action annotated (`addCase(CONSTANT, (state, action: ReturnType<typeof creator>) => ...)`), or `addMatcher` with `reducers/match_action.ts`'s `matchAction<A>(...types)`, which checks the `type` as RTK's `match` does; `compose` and `history`, plain reducers, match their whole action union with `matchAction` and `switch` on the type. Either way a constant that is not its action's `type` does not compile. On a merge, an upstream change to one of these `.js` reducers must be ported by hand into its `.ts` file (the `.js` no longer exists, so git reports a modify/delete conflict).

Status links use the accent (`--color-text-status-links: var(--color-text-brand)`), the brand hover is darker so white text stays at AA, `--dropdown-shadow` is one short soft shadow, and the rich-text (code, quote) tokens are neutral.
- `tokens/_shape.scss`: radii 4 / 6 / 8 / 10 / 12px (`--radius-xs` … `--radius-xl`).
- `styles/fonts/inter.scss`: upright Inter is the bundled variable font (`fonts/inter/inter-variable-font-slnt-wght.woff2`, OFL, already in upstream's tree) with its weight range clamped to 400–600, replacing the static regular and semibold upright faces; the italic faces are upstream's.
- `styles/mastodon/basics.scss`: `--font-body` is Inter with a system fallback stack and `--font-heading` follows it (upstream: Roboto and Syne); `html` / `body` background is `--color-bg-app`.
- `styles/mastodon/components.scss` (each block marked `tstodon theme`): `.button` (14px, 6px radius), neutral `.button.button-secondary` and `.dropdown-button`, compact `.column-link` with a solid selected row and accent icon, a hover background on timeline rows (`.status__wrapper`, `.notification-group`, `.conversation`), `.dropdown-menu` radius and neutral item hover, no glow under an active `.column-header__wrapper` or its icon, tabular numbers in `.animated-number` and `.character-counter`.

- `styles/entrypoints/pages.scss` (new, tstodon only): the stylesheet of the pages the Worker renders itself (settings, sign-in, OAuth, admin, …), built from the same token mixins (`tokens/theme/{base,dark,light}`, `tokens/{shape,type}`) and `fonts/inter.scss`. Upstream's `findEntrypoints` picks it up as an entry like `inert.scss`; `web-build.ts` hands its pack to the Worker as `pages`. It resolves `data-color-scheme="auto"` / `data-contrast="auto"` with media queries, because those pages load no `theme-selection.js`.

Outside `src/`, `packages/worker/server/web-app.ts` renders the shell's `data-color-scheme` and `data-contrast` from the viewer's appearance setting (`server/appearance.ts`; upstream's Rails layout does the same from `color_scheme` / `contrast`), `auto` for a signed-out visitor, and the `theme-color` meta values from the app backgrounds (`#08090a` dark, `#f7f8f8` light; one value when the scheme is chosen). `inline/theme-selection.js` is unchanged.

## Working on it

Change the frontend here and list each change against upstream under "Local changes" above. `pnpm dev` serves it from source with hot reload (the Worker's shell links the source entry points, Vite's HMR client and the React Refresh preamble); `pnpm build` builds it into `packages/worker/dist/client/` with the Worker. Its checks: `pnpm typecheck:web` and `pnpm test:web` (CI runs both). The Worker renders the shell from `virtual:tstodon/web-manifest` (`web-build.ts`), which names the entries `src/entrypoints/{common,application,remote_interaction_helper,theme-selection}.ts`, `src/styles/entrypoints/inert.scss` and the default theme.

How to move to a newer upstream release, including `scripts/import-mastodon-web-lock.mjs`, which locks the dependencies at the versions upstream's `yarn.lock` resolved: [docs/operations/mastodon-web-upstream.md](../../../docs/operations/mastodon-web-upstream.md).
