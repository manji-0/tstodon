1. Provision Cloudflare resources with [`infra/cloudflare`](../../infra/cloudflare/README.md) (`tofu apply`): D1, R2, the outbox Queue `tstodon-outbox-process`, its dead-letter queue `tstodon-outbox-dlq` (`outbox_dlq_name`) and the pull queue `tstodon-pull` (`pull_queue_name`). A deployment from before OPS-7 also has the KV namespaces `REMOTE_DNS_CACHE` and `APP_CACHE`, which nothing uses any more: deploy this version (it binds neither), then let `tofu apply` destroy them (see the [infra README](../../infra/cloudflare/README.md#suggested-apply-order)).
2. Copy `tofu output -json wrangler_bindings` into production `packages/worker/wrangler.jsonc`, and pin the account there (`account_id`) or export `CLOUDFLARE_ACCOUNT_ID` (replace placeholder D1 / R2 / queue identifiers; the producers `OUTBOX_PROCESS_QUEUE`, `OUTBOX_DLQ` and `PULL_QUEUE` name the three queues).
3. Put the Better Auth signing secret, once: `openssl rand -base64 32 | wrangler secret put BETTER_AUTH_SECRET` (see [Authentication](../reference/configuration.md#authentication)). Without it every request fails off localhost. It signs the user and session rows; it is not the login. Set `CF_ACCESS_TEAM_DOMAIN` and `CF_ACCESS_AUD` for the Access application. When `CF_ACCESS_ADMIN_GROUPS` is non-empty, every Access login sets or clears admin from those groups. `ADMIN_USERNAMES` grants admin only the first time that user row is created, so use it for the first admin while the group list is empty. Set `REGISTRATIONS_OPEN` / `REGISTRATION_APPROVAL` as wanted. Access already verified the email, so sign-up does not mail a confirmation link. An existing account links only when the Access email equals `access_email` exactly; another spelling creates a second account when registrations are open and locks the person out when they are closed. `signedInAt` is the Access JWT `iat`. Access can re-issue an app token from a still-valid org session, so account move, session end, and app revoke need a short Access session lifetime if you want a fresh sign-in. The server sends no mail, so there is no mail binding or sender to set up.
4. Put Cloudflare Access in front of the browser paths, not the whole site: a whole-site application blocks federation and API clients. Set `create_access = true` in [`infra/cloudflare`](../../infra/cloudflare/README.md#access), with `instance_hostname` and who may sign in (`access_allowed_emails`, `access_allowed_email_domains`, or `access_allow_everyone`), and set `CF_ACCESS_AUD` to `tofu output access_aud`. It creates a sign-in application on the hostname and a more specific bypass application on `/api/*`, `/oauth/token`, `/oauth/revoke`, `/.well-known/*`, `/users/*`, `/emojis/*` (a local custom emoji's document, which its `Emoji` tag names), `/@*`, `/inbox`, `/actor` (the instance actor and `/actor/inbox`: remote servers fetch it to verify what it signs, such as forwarded reports), `/nodeinfo`, and media (`/media/*`, `/attachments/*`, `/avatars/*`, `/headers/*`), so `/`, `/auth/*`, `/oauth/authorize`, `/settings` and `/admin` need Access and the rest answers the Worker. `/@*` is bypassed because it is a local account's and a local post's `url` (`/@name`, `/@name/id`): another server resolves a pasted link there, and the Worker sends it on to `/users/*`. A browser there carries no assertion, so the Worker reads its `CF_Authorization` cookie instead, and sends a browser without a valid one to `/auth/sign_in`, which Access protects. `/oauth/authorize` reads the Access JWT. Login is Access (its own passkeys, or an identity provider such as WorkOS, set up in the Zero Trust dashboard). API clients still send `Authorization: Bearer` tokens this server issued. Without OpenTofu, create the same two applications in the dashboard.
5. Put the Web Push key as a secret, once: `wrangler secret put VAPID_PRIVATE_JWK` (see [Web Push](../reference/configuration.md#web-push)); optionally set `VAPID_SUBJECT`.
6. Authenticate wrangler (`wrangler login`, or `CLOUDFLARE_API_TOKEN` with Workers Scripts:Edit plus read on the bound resources). The deploy step below applies remote D1 migrations itself.
7. Put the media bucket on a public hostname: set `media_hostname` and `zone_id` in [`infra/cloudflare`](../../infra/cloudflare/README.md#media-hostname) and apply, then set `MEDIA_PUBLIC_BASE_URL` to `tofu output media_public_base_url`. Object keys under the bucket are the URL path (`attachments/…`, `avatars/…`, `headers/…`). See [Configuration — Media public URLs](../reference/configuration.md#media-public-urls).
8. The same apply sets the bucket's CORS policy for browser reads of that hostname (`GET`/`HEAD` from `https://<instance_hostname>`, or `media_cors_allowed_origins`). Check it with `wrangler r2 bucket cors list <MEDIA_BUCKET_NAME>`, and purge the media hostname cache after changing CORS if the domain was already live. Without OpenTofu: copy [`infra/cloudflare/media-cors.json.example`](../../infra/cloudflare/media-cors.json.example), set `allowed.origins`, and run `wrangler r2 bucket cors set <MEDIA_BUCKET_NAME> --file infra/cloudflare/media-cors.json`. Worker media proxy CORS is separate (`Access-Control-Allow-Origin: *` on `/media/*` and object-key routes).
9. `pnpm run ci`
10. `pnpm run deploy` (`void deploy --backend cloudflare` in `packages/worker`). Void checks that every binding the source needs is in `wrangler.jsonc` with a real id and that the queue exists, builds (the Worker and its client, Mastodon's web UI from `packages/worker/src`, fetching upstream's emoji on the first build; see [Web UI](../reference/configuration.md#web-ui)), warns about secret-looking plaintext vars, validates `packages/worker/app/db/migrations/*.sql` against what wrangler would apply, applies them to remote D1 (and verifies none remain pending), then runs `wrangler deploy` on the verified build. The upload carries the generated entry, cron triggers from `packages/worker/app/crons`, and the queue consumers from `packages/worker/app/queues`: `tstodon-outbox-process` with `dead_letter_queue = tstodon-outbox-dlq` (its `deadLetterQueue` export, which `queueConsumerOptions` in `packages/worker/void-plugins.ts` writes; Void has no option for it), `tstodon-outbox-dlq`, whose consumer stores dead jobs in D1, and `tstodon-pull` (fetch work such as a remote reply's thread job, with the same dead-letter queue). All three queues must exist before the deploy. Run `pnpm -C packages/worker exec void deploy --backend cloudflare --provision` once on a dev machine to create missing D1 / R2 / Queue resources and write their ids; `--provision` is refused in CI. The managed `void deploy` (Void platform) does not fit this Worker: it ignores `wrangler.jsonc` and cannot carry the Workflow, `StreamHub`, Analytics Engine, or Images bindings.
11. Rate limits are on by default with Mastodon's numbers (see [Rate limits](../reference/configuration.md#rate-limits)). Their counters are the `RateLimitCounter` Durable Object (`RATE_LIMIT_COUNTER`, migration tag `v2` in `wrangler.jsonc`), which `wrangler deploy` creates; there is nothing to provision. Set `RATE_LIMITS` to change a bucket, and add the [edge rule](#rate-limiting-at-the-edge) below as an outer layer.
12. Re-apply Terraform with `attach_queue_consumer = true` so the three Queue consumers point at the deployed Worker. `wrangler deploy` writes the same consumers, so keep the Terraform settings equal to the queue files: `queue_consumer_batch_size`, `queue_consumer_max_retries`, `queue_consumer_max_concurrency` (default `1`) and `queue_consumer_max_wait_time_ms` to `maxBatchSize`, `maxRetries`, `maxConcurrency` and `maxBatchTimeout` in `packages/worker/app/queues/tstodon-outbox-process.ts`; `dlq_consumer_batch_size`, `dlq_consumer_max_retries` and `dlq_consumer_max_wait_time_ms` to those in `tstodon-outbox-dlq.ts`; `pull_consumer_batch_size`, `pull_consumer_max_retries`, `pull_consumer_max_concurrency` and `pull_consumer_max_wait_time_ms` to those in `tstodon-pull.ts`; and `outbox_dlq_name` to its `deadLetterQueue`. On an existing deployment, apply Terraform (step 1) to create `tstodon-outbox-dlq` and `tstodon-pull` before deploying this version (or let `void deploy --provision` create it). Inspecting and requeueing dead jobs is in the runbook ([Dead-lettered jobs](./runbook.md#dead-lettered-jobs)).

13. Schedule the encrypted D1 backup ([Scheduled D1 backups](./runbook.md#scheduled-d1-backups)): create the backup bucket in a second Cloudflare account (or another provider; `infra/cloudflare` does not create it, since it must not live in the production account) with a lock rule, an R2 API token with Object Read & Write on that bucket only, a production-account API token with Account → D1 → Edit only, and an age key pair (`age-keygen`) whose identity two custodians keep offline. Set the repository secrets `D1_BACKUP_CLOUDFLARE_API_TOKEN`, `D1_BACKUP_S3_ACCESS_KEY_ID` and `D1_BACKUP_S3_SECRET_ACCESS_KEY` and the variables `D1_BACKUP_CLOUDFLARE_ACCOUNT_ID`, `D1_BACKUP_DATABASE_ID`, `D1_BACKUP_AGE_RECIPIENTS` (public keys), `D1_BACKUP_S3_ENDPOINT` and `D1_BACKUP_S3_BUCKET`, then run the `D1 backup` workflow once by hand and restore its output with `scripts/d1-restore-check.sh`.

Never commit `BETTER_AUTH_SECRET`, VAPID keys, or other private key material. Confirm the Worker placement region still matches the D1 primary.

Then verify the deployment end to end with the [launch checklist](./launch-checklist.md) (Access paths, sign-in, media, push, rate limits, crons, backups, a federation smoke test). Backups, monitoring, incident playbooks and upgrades are the [operations runbook](./runbook.md).

## Rate limiting at the edge

<!-- constrained-by ../reference/configuration.md#rate-limits -->

The Worker's limits are per subject and Mastodon-shaped, and each counted request is a Durable Object call. A Cloudflare WAF rate-limiting rule drops a flood before it reaches the Worker, at no Worker cost, so put one in front as an outer layer. Keep it well above the Worker's own budgets so that it only ever catches floods: a client within Mastodon's limits must never meet it.

In the dashboard: the zone, **Security** → **WAF** → **Rate limiting rules** → **Create rule** (the Free plan has one rule, a 10-second period and a 10-second block; paid plans allow longer):

- **If incoming requests match** (expression editor):

  ```text
  (http.request.uri.path wildcard "/api/*"
   or http.request.uri.path wildcard "/oauth/*"
   or http.request.uri.path wildcard "/auth/*"
   or http.request.uri.path wildcard "/.well-known/*"
   or http.request.uri.path wildcard "/users/*"
   or http.request.uri.path wildcard "/emojis/*"
   or http.request.uri.path eq "/inbox"
   or http.request.uri.path eq "/actor/inbox")
  and not http.request.uri.path wildcard "/api/v1/streaming*"
  ```

- **With the same characteristics**: IP.
- **When rate exceeds**: 200 requests per 10 seconds.
- **Then take action**: Block, for 10 seconds (on a paid plan, a custom JSON response `{"error":"Too many requests"}` with status 429 matches what the Worker sends). Do not use a challenge: API clients and remote servers cannot solve one.

Remote servers deliver from a few addresses and retry a refused delivery later, so a 10-second block costs them only a delay; still, if a large server that many of your users follow is caught by the rule, raise the rate or exclude the inbox paths from it and leave them to `inbox_ip` / `inbox_domain`.
