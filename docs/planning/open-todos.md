- Quote retries and refresh (#79, Q-4), on the existing `tstodon-outbox-process` queue as two new `OutboxJob` kinds; no new queue, binding or migration. A pending quote by a remote note was verified again only by the note's next `Update`, and an accepted quote's stamp was never checked again. As Mastodon's `fetch_and_verify_quote`, `syncRemoteQuote` (`server/remote-quote.ts`) now queues `RefetchAndVerifyQuote { quoteId, quotedUri, approvalUri, attempt }` (`enqueueQuoteRefetch`, `server/quote-retry-queue.ts`) when a quote of a remote status is left pending with its quoted note unresolved (a failed fetch, or past `MAX_QUOTE_DEPTH`, Mastodon's `RecursionLimitExceededError`) or with a stamp fetch that failed for now (5xx, network); the stamp is fetched in `syncRemoteQuoted` to tell that apart from a stamp that does not match, which queues nothing. The job (`processRefetchAndVerifyQuoteJob`, `server/quote-retry-jobs.ts`, Mastodon's `RefetchAndVerifyQuoteWorker`) is dropped when the quote is gone, no longer pending, names another quoted note, or its author is gone, suspended or outside the allow list; otherwise it runs the same verification under the same quote id (`reverifyRemoteQuote`), so a stamp that verifies accepts the quote, one that no longer resolves (4xx) rejects it, and a change is announced with `status.update` on the local timelines showing the note (`announceRemoteQuoteChange`, `server/remote-quote-announce.ts`, now shared with the inbox). A quote still left pending is queued again until four attempts (Sidekiq's `retry: 3` plus the first run); the delays come from `QuoteRetry` (`packages/domain/src/quote-retry.ts`): 30 to 600 seconds before the first (`perform_in(rand(30..600))`), then `ExponentialBackoff`'s `15 + 10n⁴ + rand(10n⁴)` seconds, sent with the queue's `delaySeconds`. - Distinct ids within an isolate (#52). Fifty-one parallel posts in a worker test could answer 500 with `UNIQUE constraint failed: outbox_deliveries.id`. An id is the millisecond shifted left 16 bits with 16 random low bits below it. workerd advances `Date.now()` only on I/O, so a burst shares milliseconds (510 parallel posts made 1530 ids in 456 milliseconds, up to 12 in one), and two ids in one millisecond matched with probability 1 in 65,536 per pair. `entityIdAt` (`server/ids.ts`) still draws the low bits uniformly at random, and now remembers which low values it handed out at each millisecond and draws again on a repeat. The low bits stay random because an id is the only secret guarding a media attachment: its R2 key is `attachments/<accountId>/<mediaId>`, served without auth, and `GET /media/:id` needs only the id. A sequential counter would let anyone who sees one id narrow the search for a neighbor's. The isolate remembers at most 65,536 low values and 256 milliseconds, forgetting the oldest milliseconds first and never the one being drawn. Once all 65,536 values at one millisecond are used, `entityIdAt` throws instead of moving to another millisecond, since a later one could sort after `Date.now()`. A backfill of posts published in the same second no longer collides with itself, and an id still never sorts after its instant, so `max_id` paging is unchanged. Ids from two isolates can still match at one instant (1 in 65,536 per pair), so the remote-status retry from #38 stays; `rerollEntityId` marks the collided low value used and draws a fresh random one. The poll backlog test creates its 51 polls in parallel again.

- Data export and import (WEB-3). `/settings/export` downloads Mastodon's CSV files (`/settings/exports/{follows,lists,blocks,mutes,domain_blocks,bookmarks}.csv`, same columns and headers: follows `Account address,Show boosts,Notify on new posts,Languages`, mutes `Account address,Hide notifications`, the rest headerless). Local accounts are `user@<domain>`, remote ones `user@host` from the cached actor; `server/csv-export.ts` streams a response from `listEntriesPage` (`server/csv-entries-store.ts`, keyset pages of `EXPORT_PAGE_SIZE` = 200). `/settings/import` (also `/settings/imports`) takes a multipart upload of one type (the domain `ImportType` union: `Following`, `Lists`, `Blocks`, `Mutes`, `DomainBlocks`, `Bookmarks`) in one `ImportMode` (`Merge`, `Overwrite`); `/settings/imports/:id` shows progress and the failed rows. Limits are named constants in `server/csv-import-file.ts`: `MAX_IMPORT_BYTES` (1 MiB, checked against `Content-Length` before the body is read, then against the file), `MAX_IMPORT_ROWS` (5000 data rows, a bigger file is refused whole), per-cell caps, a UTF-8 and RFC 4180 parse (`server/csv.ts`, at most `CSV_MAX_COLUMNS` columns). Mastodon allows 20 MB; the lower caps bound a Worker's memory and the D1 rows one file stores. A row is validated by the same handle pattern as account lookups (no `/`, `#`, `?`, second `@`), domain host names, and local status URLs only. The file is stored as `csv_imports` and `csv_import_rows` (migration 0095) with a per-row `Pending`/`Applied`/`Failed` outcome (domain `RowOutcome`, failures `Malformed`, `UnknownAccount`, `Refused`, `NotFollowed`, `Unsupported`). A `ProcessCsvImport` queue job applies `IMPORT_PAGE_SIZE` (10) rows per run, resolves each handle (local lookup, cached remote actor, else WebFinger through `resolveAccountHandle`) and calls the existing follow (`followAccountRef`, extracted from `MoveFollows`), block, mute, domain block, list member and bookmark functions, then queues the next page `IMPORT_PAGE_DELAY_SECONDS` (2) later; one import runs per account (a `Queued` import older than 6 hours, or one whose job the queue gave up on, is `Failed`, shown as stopped, and stops blocking), and the latest `IMPORTS_KEPT` (5) are kept. An overwrite then pages through the account's existing entries and removes the ones the file does not name (for lists, only in lists the file names); it is refused at upload (a 303 back to the page with the reason) when a row cannot be read, since that row's entry could not be matched. Each row that resolves records the account it resolved to (`csv_import_rows.resolved`), and the overwrite keeps entries by that, not by the handle text, so a handle whose WebFinger domain differs from its actor's host (`harasser@example.com` served by `social.example.com`) is not pruned; a row that did not resolve still protects entries with the same handle text. A first row is a header only when every cell is a known column name and it is not itself a valid row, so a list called `title` or a user `acct` is data. Not done: a followed account in a list import is not followed for the user (a list takes accounts already followed, as the list API does), requested (not yet accepted) follows are neither exported nor removed by an overwrite, bookmarks of posts on other servers cannot exist here so they fail as `Unsupported`, and cells starting with `=`, `+`, `-`, `@`, tab, or CR (list titles, remote usernames) are exported with a leading `'` (cells starting with `'` get a second one) which an import strips (`guardCell`/`unguardCell` in `server/csv.ts`). One import page is `IMPORT_PAGE_SIZE` rows, but the consumer takes up to 10 jobs per invocation, so the lookup rate is bounded per import, not per server.

- Remote profile backfill. A view of `GET /api/v1/accounts/r_…/statuses` claims the actor with one `UPDATE` on `remote_actors.outbox_fetched_at` (`OUTBOX_BACKFILL_TTL_MS`, 24h) and queues one `BackfillRemoteOutbox { actorUri }` job; the response shows what is cached. `remote_actors` now keeps `outbox_uri` and `featured_uri` from the actor document (migration 0082); an actor cached before that is refetched once by the job. Per page: a public or unlisted `Create` of the actor's own note from its host is stored through `persistRemoteObject`, an `Announce` through `persistAnnouncedObject` (third-party origin checks) and `recordRemoteBoost`; embedded objects from another host or attributed to someone else are not trusted, and cached items are no-ops. The job walks up `in_reply_to_uri` and stores up to `THREAD_BACKFILL_ANCESTOR_LIMIT` (5) missing ancestors through `persistAnnouncedObject` (its origin checks and author resolution), then reads the status's own `replies` collection (embedded or linked, first page) and stores up to `THREAD_BACKFILL_REPLY_LIMIT` (20) of them; nothing is fanned out, and the next view shows the result. - Remote profile backfill. A view of `GET /api/v1/accounts/r_…/statuses` claims the actor with one `UPDATE` on `remote_actors.outbox_fetched_at` (`OUTBOX_BACKFILL_TTL_MS`, 24h) and queues one `BackfillRemoteOutbox { actorUri }` job; the response shows what is cached. `remote_actors` now keeps `outbox_uri` and `featured_uri` from the actor document (migration 0082); an actor cached before that is refetched once by the job. The job reads the outbox's first page, at most `OUTBOX_BACKFILL_ITEM_LIMIT` (20) items: a public or unlisted `Create` of the actor's own note from its host is stored through `persistRemoteObject`, an `Announce` through `persistAnnouncedObject` (third-party origin checks) and `recordRemoteBoost`; embedded objects from another host or attributed to someone else are not trusted, and cached items are no-ops. Backfilled notes and boosts take ids from their `published` time (`entityIdAt`, zero-padded to 18 digits so string order is time order before mid-2018), as Mastodon's Snowflake ids do, so they sort where they were written on the profile, home, and lists instead of looking new; nothing is fanned out and no mention is notified. The `featured` collection (same cap) fills `remote_actor_pins` (migration 0083), replaced on each backfill and kept when the collection cannot be read; `pinned=true` on a remote profile lists those notes. Not done: a second outbox page, account lookup triggering a backfill, and backfilling replies or threads.
- Remote accounts on profiles and lists. `GET /api/v1/accounts/r_…/statuses` lists the cached actor's notes and boosts, newest first, with `max_id`/`since_id`/`min_id`, `limit`, `exclude_replies`, `exclude_reblogs`, `only_media`, and `tagged` (the last three leave boosts out, as in Mastodon). Public and unlisted entries are open to everyone, followers-only ones to accepted followers, and notes that mention the viewer to that viewer. A boost needs a public or unlisted target whose author the viewer does not block or mute. The list is empty when the viewer blocks the actor or its domain or the instance suspends that domain, and for `pinned=true`. An uncached actor answers 404. A list member is now `{ kind: "LocalAccount", accountId } | { kind: "RemoteActor", actorUri }`. Remote members live in `account_list_remote_members` (migration 0081: `list_id`, `outbound_follow_id`, both `ON DELETE CASCADE`). Mastodon's `ListAccount` belongs to a `Follow` in the same way, so unfollowing, a `Reject`, a `Move`, or an actor purge drops the memberships. `POST /api/v1/lists/:id/accounts` takes `r_…` ids of accepted follows and answers 422 for any other remote account, adding nothing. `DELETE`, `GET /api/v1/lists/:id/accounts`, and `GET /api/v1/accounts/r_…/lists` handle both kinds. The list timeline uses the same pipeline as home (`feedDocuments` in `server/timeline-documents.ts`, with a `FollowedFeed` of `Home` or `List`), so blocks, mutes, muted conversations, domain blocks, filters, and the follow's `languages`/`reblogs` apply to remote members' notes and boosts. It now pages by all three id cursors. `replies_policy: none` drops remote replies, and `followed` keeps those that answer a followed remote actor. Not done: carrying list memberships over on a `Move` as Mastodon does, and the `list` stream.

- Public, hashtag, and list streaming. Each streaming socket keeps its own subscriptions in its WebSocket attachment (so hibernation keeps them): the `stream` query parameter (with `tag` / `list`) and later `subscribe` / `unsubscribe` messages, which is how the web UI multiplexes every column over one socket. The streams are `user`, `user:notification`, `direct`, `public`, `public:local`, `public:remote`, their `:media` variants, `hashtag`, `hashtag:local`, and `list`. Each event is tagged with the stream it was subscribed on (`["hashtag", "cats"]`, `["list", "<id>"]`); notifications now reach `user` sockets as `["user"]`, since the web UI ignored the old `["user", "user:notification"]`. `user*` and `direct` need the token's account, a list its owner (`Not authorized to stream this list`), and public and hashtag streams are open without a token, as their timelines are. Scopes follow Mastodon's streaming server: `user`, `list`, and `direct` need `read` or `read:statuses`, `user:notification` needs `read` or `read:notifications`, `user` carries notification events only when the token also has `read:notifications`, and public and hashtag streams need no scope; a refusal is the `{"error": "Access token does not have the required scopes", "status": 401}` frame on connect and on `subscribe`. The socket attachment keeps two flags derived from the scopes. The `direct` stream carries `conversation` events: a new local direct note (author and mentioned local accounts) or remote direct note mentioning a local account sends each of them the Conversation entity their conversation list would show (`publishConversationUpdate`), so a blocked or muted author, or a conversation the account removed, sends nothing. Marking a conversation read (`POST /api/v1/conversations/:id/read`) sends the account's own `direct` streams the updated entity (`unread: false`, `publishConversationRead`); removing one sends nothing, as in Mastodon, where only the account conversation's update pushes. A `StreamHub` mirrors its sockets' public, hashtag, and list subscriptions into `stream_subscriptions` (migration 0084), one row per distinct channel: inserted before the first socket takes it and deleted after the last lets go, with every change run in arrival order; a row left behind is removed when a fan-out finds no socket behind it. A hashtag stream needs a hashtag name (letters, digits, underscores, at least one letter, at most 100 UTF-16 units; otherwise `Invalid tag name parameter`). A socket holds at most 32 streams (`MAX_SOCKET_CHANNELS`) and a hub at most 32 distinct hashtag and list streams (`MAX_HUB_TAGGED_CHANNELS`, public streams not counted); past either the subscribe gets a 429 error frame and no row. Every anonymous socket shares one hub, so they share those 32: one client holding them all keeps other anonymous sockets off new hashtags until it lets go. A public local note, a public remote note delivered live to the inbox (never a backfilled one), and their edits and deletes queue `FanOutPublic { event, entryId, afterHub }`. It pages the hubs holding a public or hashtag subscription that may carry the status (20 per job) and asks `publicTimelineDocuments` / `tagTimelineDocuments` (the functions the REST timelines use) for that one entry for the hub's viewer, so blocks, mutes, domain blocks, and `filtered` apply as on the timeline; `delete` goes to every public and hashtag subscription. The home fan-out also looks up its page of followers' open list streams and asks `listTimelineDocuments` for the entry. Cost: one query per page of hubs, then one timeline query per matching subscription per hub (not per socket); hubs without such a subscription cost nothing. A page stops before the hub that would take it past 38 timeline passes and queues the rest. A hashtag matches when the status's text holds `#tag` as a plain substring (local) or its `remote_status_tags` row (remote); local statuses still have no tag table, so `#cats` also matches `#catsitting`, as the tag timeline does. The public and tag timelines now also leave out authors the viewer blocks or mutes, in their queries so a page is filled past them, and the public timeline takes `only_media`. Server-sent events: a GET without an upgrade on `/api/v1/streaming/user`, `/user/notification`, `/direct`, `/public[/local|/remote][/media]` (or `?only_media=true`), `/hashtag[/local]?tag=`, `/list?list=` answers a `text/event-stream` of `event:` / `data:` frames (the WebSocket payload without the `stream` tag), `:)` first and a `:thump` comment every 15 s (`SSE_HEARTBEAT_MS`); `/api/v1/streaming/health` answers `OK` to anyone. The token comes from `Authorization` or `access_token`, and scope checks, refusals (401 with Mastodon's `error` body, 400 for a missing or invalid tag, 404 for an unknown path), and the 32-tagged-stream hub cap are the WebSocket's (`requestStreamChannel`, `StreamHub.admit`). One SSE connection holds one stream. The hub keeps its `ReadableStream` controller in memory and writes to it from `publish`; the open response keeps the Durable Object awake (no hibernation while any SSE client is connected, so each connection bills duration), and a client disconnect (`cancel`) clears the heartbeat and drops the `stream_subscriptions` row once no other socket or connection holds it. A hub restarted by a deploy loses its SSE connections and leaves their rows to the next fan-out. A client that stops reading is dropped after 256 queued frames. There is no cap on SSE connections per hub beyond the tagged-stream one. Not done: sharding the anonymous hub (every anonymous socket and SSE connection shares one hub and the 32 tagged-stream budget; sharding would need the public fan-out to find every shard).
- Home streaming like Mastodon's `FanOutOnWriteService`: a local post, local boost, local edit, local delete, and unboost, and an inbox `Create`, `Announce`, `Undo{Announce}`, `Delete`, and note `Update` from a remote actor, queue a `FanOutHome { event, entryId, author, afterAccountId }` job. The job pages the author's local followers (accepted local `follows` and accepted `outbound_follows`), 20 per job, and chains a job for the next page, like `MoveFollows`. For `update` and `status.update`, each follower gets the entry only when `homeTimelineDocuments` (the function `GET /api/v1/timelines/home` uses) returns it for that follower under the `onlyId` cursor. So blocks, mutes, muted conversations, domain blocks, and follow `reblogs`/`languages` apply as on the timeline, and the document is rendered for that follower, with its `filtered` matches. `delete` goes to every follower. A redelivered job only re-sends the events. The author still hears its own post at once, and now also its boost, edit (as `status.update`), delete, and unboost. The `list` streams ride on this fan-out (see public, hashtag, and list streaming above). A deleted status, local or remote, takes the local boosts of it with it and tells the boosters and their followers (`announceRemovedBoosts`: `delete` on the booster's streams and a `FanOutHome` `delete` for each boost id). A local delete removes them in the same batch as the status (`deleteStatus`, since the foreign key would only null their target), a remote `Delete` collects them before the `reblog_of_remote_id` cascade (`deleteRemoteStatusByObjectUri`), and a purge of the actor does the same for all its statuses. A deleted actor's statuses are announced to its followers as described under the inbox account `Delete`.

- Remote boosts on home: a signed inbox `Announce` of a local note or of a remote note becomes a `remote_boosts` row (migration 0080: its own id from the status id space, the booster's `actor_uri`, the unique `activity_id`, exactly one of `local_status_id` / `remote_status_id`, the `Announce`'s visibility from its `to`/`cc`, `published_at`). As in Mastodon, only a public or unlisted status can be boosted, a direct `Announce` is dropped, and an actor keeps one boost per status. A remote note that is not cached yet is fetched from its URI: the booster's own note may come embedded, another actor's note must name that URI as its id and come from its author's host, and is stored under its author. A local note still gets its `remote_announces` row and the author's `reblog` notification. `Undo{Announce}` signed by the booster deletes the row by the Announce id; deleting the boosted status or purging the booster cascades. The home timeline merges the boosts of accepted remote follows with `reblogs` on, by the same id cursors, leaving out blocked or muted boosters and original authors and their blocked or suspended domains. A boost renders as a Mastodon status with the booster as `account`, the local or remote status as `reblog`, and the `Announce` id as `uri`, and `GET /api/v1/statuses/:id` serves it (a followers-only boost only to the booster's followers). Not done: remote boosts on public and tag timelines (Mastodon keeps boosts off them), `filtered` and muted threads on boosts, and Mastodon's reblog aggregation on home.

- Account migration, as Mastodon's: `/settings/aliases` and `/settings/migration` are server-rendered pages in the style of the sign-in pages (Mastodon keeps both in Rails views, outside the web app), driven by the Better Auth session cookie with the same-origin form check. An alias ("moving from") resolves a handle by WebFinger, or a bare or local-domain username to a local account, and is stored in `account_aliases` (migration 0085); the actor document lists the aliases as `alsoKnownAs`. A move ("moving to") resolves the new account, reads its `alsoKnownAs` fresh (a remote document is fetched, a local account's aliases are read from D1), and refuses when this account is missing. It needs a session under `RECENT_SIGN_IN_WINDOW_MS` (10 minutes, `server/recent-sign-in.ts`) old; the page signs in again with the passkey first when it is older, since there is no password to ask for. The move is recorded in `account_moves` (migration 0086, one row per account) by one conditional upsert that enforces `MOVE_COOLDOWN_MS` (30 days) before moving elsewhere; repeating the same move resends the `Move` and keeps the time. A `Move{actor, object: self, target}` goes through `ExpandFollowers`, so remote followers sharing an inbox get it once. Local followers move through the paged `MoveFollows` path the inbound `Move` uses (`moveFollowPage` takes `AccountRef`s for both ends): a local follow of the new account, or an outbound follow when it is remote, then the unfollow and a `move` notification. The account renders `moved` and the actor `movedTo`. An inbound `Move` to a local target now reads the target's aliases from D1 instead of fetching its own actor URL, and a remote account moved to a local one renders it under `moved`. The web UI reaches both pages through `/settings/preferences` (see "Settings from the web UI").
- Account migration follow-ups (#11). Federation: `sendActorUpdate` (`server/local-actor.ts`, which also builds the actor document the route serves) queues an `Update{object: <Person>}` through `ExpandFollowers` after a move and after a cancel, so remote servers that cached the actor see `movedTo` appear or go. An inbound actor `Update` now sets `remote_actors.moved_to` when its `movedTo` names an account whose document lists the signer in `alsoKnownAs` (same check as a `Move`), and clears it when the document names none; only a `Move` carries followers over. A server that has no follower of the account left (all moved) hears nothing from the cancel's `Update`, as in Mastodon. Cancel: `POST /settings/migration/cancel` ("Cancel redirect" on the page, no re-authentication as in Mastodon) sets `account_moves.cancelled_at` (migration 0091). The row stays, so the cooldown still counts from `moved_at` and applies to any new move, the cancelled target included; `findAccountMove` answers the standing move only (actor, `moved`, limits), `findAccountMoveRecord` answers `Moved | Cancelled` for the cooldown. Carry-over (`server/move-carry.ts`, as `MoveWorker`): the `MoveFollows` job gained `phase` (`follows`, `notes`, `blocks`, `mutes`; a queued job without it is `follows`) and `moveCarryPage` walks the phases one page of `MOVE_PAGE_SIZE` each, so a request costs at most four pages and larger audiences chain jobs. Blocks and mutes: carried for local accounts that do not already block/mute or follow `to` (the old block/mute stays), mutes with the same notification choice and no expiry, an expired mute is dropped, and each new block or mute leaves a note ("which you had blocked/muted") when the account has none. Fixed on the way: account notes on remote accounts were never shown in the relationship or cleared (read and delete used the `r_` id, not the actor URI). Not done: the remaining `require_user!` endpoints (unfollow, unfavourite, unboost, delete, bookmarks, lists, blocks and mutes, polls, media, settings) and Mastodon's redirect of the web UI to the settings pages for a moved login; a list membership of a local `from` for an account that does not follow it.

- A followed remote account moving: an inbox `Move{object: A, target: B}` signed by A counts only when `object` is the signer and B's actor document, fetched fresh through the federated fetch (allow list and suspended domains apply), lists A in `alsoKnownAs`; anything else is a 202 no-op. B is cached and A's `remote_actors.moved_to` (migration 0077, written only by a verified `Move`, untouched by actor refreshes) points at it, so `GET /api/v1/accounts/r_A` renders `moved` with B's account. A follower who blocks B, has a domain block for B's domain, or whose federation limits refuse B keeps the follow of A and gets nothing. The work is idempotent (a redelivered `Move` finds no rows left). Fan-out is paged: the `Move` itself moves the first `MOVE_PAGE_SIZE` (50) follows in id order (index in migration 0079) and a full page queues a `MoveFollows { fromActorUri, toActorUri, afterId }` job on `OUTBOX_PROCESS_QUEUE` for the next, so one request does bounded work and large followings need no inline cap. Follow-ups: retrying a `Move` whose target fetch failed (the inbox records the activity id first, so a redelivery is dropped), `move` in grouped notifications' push alerts.

- Following remote accounts: `POST /api/v1/accounts/r_…/follow` records the follow in `outbound_follows` (migration 0076, one row per account and actor with its `follow_activity_id`, `state` `Requested` or `Accepted`, and the `reblogs`/`notify`/`languages` options) and sends `Follow` to the actor's inbox once; following again only updates the options.
