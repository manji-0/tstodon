## Done recently (do not re-open)

- A follow's notification ends with the follow (#58). Ending a follow left the target's `follow` or `follow_request` notification in place, so "X followed you" stayed after an unfollow, a withdrawn or rejected request, a removed follower or a block. Mastodon destroys the notification with the `Follow` or `FollowRequest` (`has_one :notification, dependent: :destroy`), and `AuthorizeFollowService` creates no `follow` notification when it authorizes a request. Migration 0102 adds triggers on `follows` (sender by account id) and `remote_follows` (sender by actor URI) that delete the notification when the row is deleted, and the `follow_request` one when the row leaves `Pending` / `Queued`, so every path (including blocks, admin domain blocks and account deletion) drops it. A held notification leaves the notification requests through the `notification_requests` cascade. The migration also deletes the follow notifications earlier ended follows left behind. `Undo(Follow)` no longer deletes them itself, so `RemoteNotificationWithdrawal` always names a status. Tests: `src/follow-notification-ends.test.ts`.
- Distinct ids within an isolate (#52). Fifty-one parallel posts in a worker test could answer 500 with `UNIQUE constraint failed: outbox_deliveries.id`. An id is the millisecond shifted left 16 bits with 16 random low bits below it. workerd advances `Date.now()` only on I/O, so a burst shares milliseconds (510 parallel posts made 1530 ids in 456 milliseconds, up to 12 in one), and two ids in one millisecond matched with probability 1 in 65,536 per pair. `entityIdAt` (`src/ids.ts`) still draws the low bits uniformly at random, and now remembers which low values it handed out at each millisecond and draws again on a repeat. The low bits stay random because an id is the only secret guarding a media attachment: its R2 key is `attachments/<accountId>/<mediaId>`, served without auth, and `GET /media/:id` needs only the id. A sequential counter would let anyone who sees one id narrow the search for a neighbor's. The isolate remembers at most 65,536 low values and 256 milliseconds, forgetting the oldest milliseconds first and never the one being drawn. Once all 65,536 values at one millisecond are used, `entityIdAt` throws instead of moving to another millisecond, since a later one could sort after `Date.now()`. A backfill of posts published in the same second no longer collides with itself, and an id still never sorts after its instant, so `max_id` paging is unchanged. Ids from two isolates can still match at one instant (1 in 65,536 per pair), so the remote-status retry from #38 stays; `rerollEntityId` marks the collided low value used and draws a fresh random one. The poll backlog test creates its 51 polls in parallel again.

- Final poll counts at expiry and non-filterable notification types (#44). When the `ProcessExpiredPolls` run claims an ended local poll, it queues the poll's `DistributePollUpdate` (`scheduleFinalPollUpdate` in `src/poll-update.ts`) with no delay, as Mastodon's `PollExpirationNotifyWorker` does. Remote servers then get an `Update(Question)` with `closed`, `endTime`, the final `replies.totalItems`, and `votersCount`. A redelivered run claims nothing, so it queues nothing. The job takes the poll's `update_queued_at` slot, so when a vote's debounced job is still queued, that job runs after the end and sends the final counts instead. A poll that hides its totals now federates them once it has ended, as Mastodon's `show_totals_now?` (`expired? || !hide_totals?`). A run whose batch of 50 ended polls or 50 voters was full, and that claimed at least one, queues the next `ProcessExpiredPolls` at once instead of waiting up to an hour for the cron. A run that claims nothing never chains, so a batch that keeps failing waits for the cron. `POLICY_EXEMPT_KINDS` (`src/notify.ts`) is now the set that Mastodon 4.5 marks `filterable: false` in `Notification::PROPERTIES`: `status`, `poll`, `update`, `quoted_update`, `severed_relationships`, `moderation_warning`, `annual_report`, `admin.sign_up`, and `admin.report`. So an `update` to a booster whose policy drops strangers is delivered. The block, notification-mute, and domain-block check now runs inside `deliverNotification` for every notification of every kind, before the policy, as in Mastodon's `NotifyService`. Before, only `notifyFromLocal` and `notifyFromRemote` made it, so a local `mention`, `status`, `reblog`, `favourite`, `quote`, or `quoted_update` could reach a recipient who blocks the sender or mutes its notifications, and be streamed and pushed. The moderation kinds get the same check, as in Mastodon, so an admin who blocks a reporter gets no `admin.report` from them. `notifyFromLocal` is gone, and `notifyFromRemote` only fills in the remote sender.

- A block ends the follows both ways (#49). `blockAccount` only wrote the `blocks` row, so a blocked account kept following the blocker, stayed on the blocker's lists and in both follow counts. `blockAccountTarget` (`src/account-block.ts`) now does what Mastodon's `BlockService` does: it deletes the blocker's follow or request of the target (`unfollowAccount`, or `unfollowRemoteActor` with its `Undo(Follow)`) and the target's follow or request of the blocker (`unfollowAccount`, or `removeRemoteFollower` in `src/remote-follower.ts` with its `Reject(Follow)`, which `remove_from_followers` now uses too), after writing the block, and sends a remote target the `Block` (Mastodon's id, `{actor}#blocks/{id}`). The block is written first and each severing step is best effort (a failure logs `BlockFollowNotSevered`), so a storage failure cannot leave the follows half gone with no block. `unblockAccountTarget` sends the `Undo(Block)`. The API, the CSV block import and a move's carried blocks all go through it. The list trigger of migration 0101 removes the target from the blocker's lists, and a remote member leaves with its outbound follow. An inbound `Block` (`src/inbox/block.ts`) ends the follows with the local account the same way, as Mastodon's `ActivityPub::Activity::Block`, but tstodon does not record that a remote actor blocks a local account. An inbound `Follow` (`src/inbox/follow.ts`) from an actor the target blocks, by account or by account domain block, is answered with `Reject(Follow)` and stores nothing, as Mastodon's `ActivityPub::Activity::Follow`; a local signer the target blocks is refused the same way.

- Public, hashtag, and list streaming. Each streaming socket keeps its own subscriptions in its WebSocket attachment (so hibernation keeps them): the `stream` query parameter (with `tag` / `list`) and later `subscribe` / `unsubscribe` messages, which is how the web UI multiplexes every column over one socket. The streams are `user`, `user:notification`, `direct`, `public`, `public:local`, `public:remote`, their `:media` variants, `hashtag`, `hashtag:local`, and `list`. Each event is tagged with the stream it was subscribed on (`["hashtag", "cats"]`, `["list", "<id>"]`); notifications now reach `user` sockets as `["user"]`, since the web UI ignored the old `["user", "user:notification"]`. `user*` and `direct` need the token's account, a list its owner (`Not authorized to stream this list`), and public and hashtag streams are open without a token, as their timelines are. Scopes follow Mastodon's streaming server: `user`, `list`, and `direct` need `read` or `read:statuses`, `user:notification` needs `read` or `read:notifications`, `user` carries notification events only when the token also has `read:notifications`, and public and hashtag streams need no scope; a refusal is the `{"error": "Access token does not have the required scopes", "status": 401}` frame on connect and on `subscribe`. The socket attachment keeps two flags derived from the scopes. The `direct` stream carries `conversation` events: a new local direct note (author and mentioned local accounts) or remote direct note mentioning a local account sends each of them the Conversation entity their conversation list would show (`publishConversationUpdate`), so a blocked or muted author, or a conversation the account removed, sends nothing. Marking a conversation read (`POST /api/v1/conversations/:id/read`) sends the account's own `direct` streams the updated entity (`unread: false`, `publishConversationRead`); removing one sends nothing, as in Mastodon, where only the account conversation's update pushes. A `StreamHub` mirrors its sockets' public, hashtag, and list subscriptions into `stream_subscriptions` (migration 0084), one row per distinct channel: inserted before the first socket takes it and deleted after the last lets go, with every change run in arrival order; a row left behind is removed when a fan-out finds no socket behind it. A hashtag stream needs a hashtag name (letters, digits, underscores, at least one letter, at most 100 UTF-16 units; otherwise `Invalid tag name parameter`). A socket holds at most 32 streams (`MAX_SOCKET_CHANNELS`) and a hub at most 32 distinct hashtag and list streams (`MAX_HUB_TAGGED_CHANNELS`, public streams not counted); past either the subscribe gets a 429 error frame and no row. Every anonymous socket shares one hub, so they share those 32: one client holding them all keeps other anonymous sockets off new hashtags until it lets go. A public local note, a public remote note delivered live to the inbox (never a backfilled one), and their edits and deletes queue `FanOutPublic { event, entryId, afterHub }`. It pages the hubs holding a public or hashtag subscription that may carry the status (20 per job) and asks `publicTimelineDocuments` / `tagTimelineDocuments` (the functions the REST timelines use) for that one entry for the hub's viewer, so blocks, mutes, domain blocks, and `filtered` apply as on the timeline; `delete` goes to every public and hashtag subscription. The home fan-out also looks up its page of followers' open list streams and asks `listTimelineDocuments` for the entry. Cost: one query per page of hubs, then one timeline query per matching subscription per hub (not per socket); hubs without such a subscription cost nothing. A page stops before the hub that would take it past 38 timeline passes and queues the rest. A hashtag matches when the status's text holds `#tag` as a plain substring (local) or its `remote_status_tags` row (remote); local statuses still have no tag table, so `#cats` also matches `#catsitting`, as the tag timeline does. The public and tag timelines now also leave out authors the viewer blocks or mutes, in their queries so a page is filled past them, and the public timeline takes `only_media`. Server-sent events: a GET without an upgrade on `/api/v1/streaming/user`, `/user/notification`, `/direct`, `/public[/local|/remote][/media]` (or `?only_media=true`), `/hashtag[/local]?tag=`, `/list?list=` answers a `text/event-stream` of `event:` / `data:` frames (the WebSocket payload without the `stream` tag), `:)` first and a `:thump` comment every 15 s (`SSE_HEARTBEAT_MS`); `/api/v1/streaming/health` answers `OK` to anyone. The token comes from `Authorization` or `access_token`, and scope checks, refusals (401 with Mastodon's `error` body, 400 for a missing or invalid tag, 404 for an unknown path), and the 32-tagged-stream hub cap are the WebSocket's (`requestStreamChannel`, `StreamHub.admit`). One SSE connection holds one stream. The hub keeps its `ReadableStream` controller in memory and writes to it from `publish`; the open response keeps the Durable Object awake (no hibernation while any SSE client is connected, so each connection bills duration), and a client disconnect (`cancel`) clears the heartbeat and drops the `stream_subscriptions` row once no other socket or connection holds it. A hub restarted by a deploy loses its SSE connections and leaves their rows to the next fan-out. A client that stops reading is dropped after 256 queued frames. There is no cap on SSE connections per hub beyond the tagged-stream one. Not done: sharding the anonymous hub (every anonymous socket and SSE connection shares one hub and the 32 tagged-stream budget; sharding would need the public fan-out to find every shard).
- Home streaming like Mastodon's `FanOutOnWriteService`: a local post, local boost, local edit, local delete, and unboost, and an inbox `Create`, `Announce`, `Undo{Announce}`, `Delete`, and note `Update` from a remote actor, queue a `FanOutHome { event, entryId, author, afterAccountId }` job. Limits of a moved account: Mastodon 4.4 refuses a moved user in `Api::BaseController#require_user!` (`User#functional?` is false once `moved_to_account_id` is set: 403 `Your login is currently disabled`), which every authenticated controller calls. `requireFunctionalUser` (`src/http.ts`) gives that answer for posting, editing, following, favouriting and boosting; the other write endpoints and reads still work. Not done: the remaining `require_user!` endpoints (unfollow, unfavourite, unboost, delete, bookmarks, lists, blocks and mutes, polls, media, settings) and Mastodon's redirect of the web UI to the settings pages for a moved login; a list membership of a local `from` for an account that does not follow it.

- A followed remote account moving: an inbox `Move{object: A, target: B}` signed by A counts only when `object` is the signer and B's actor document, fetched fresh through the federated fetch (allow list and suspended domains apply), lists A in `alsoKnownAs`; anything else is a 202 no-op. B is cached and A's `remote_actors.moved_to` (migration 0077, written only by a verified `Move`, untouched by actor refreshes) points at it, so `GET /api/v1/accounts/r_A` renders `moved` with B's account. Every local `outbound_follows` row of A (`Requested` or `Accepted`) moves as in Mastodon's `UnfollowFollowWorker`: follow B as `Requested` with the same reblogs/notify/languages and send `Follow` to B's inbox (a follow of B that already exists is kept untouched), then delete the follow of A and send it `Undo(Follow)`, then notify the follower with a `move` notification (`account` A, `target` B via `notifications.target_account_id`, migration 0078). A follower who blocks B, has a domain block for B's domain, or whose federation limits refuse B keeps the follow of A and gets nothing. The work is idempotent (a redelivered `Move` finds no rows left). Fan-out is paged: the `Move` itself moves the first `MOVE_PAGE_SIZE` (50) follows in id order (index in migration 0079) and a full page queues a `MoveFollows { fromActorUri, toActorUri, afterId }` job on `OUTBOX_PROCESS_QUEUE` for the next, so one request does bounded work and large followings need no inline cap. Followers of local accounts need nothing: B sends its own `Follow`, as Mastodon expects. Follow-ups: retrying a `Move` whose target fetch failed (the inbox records the activity id first, so a redelivery is dropped), `move` in grouped notifications' push alerts.

- Following remote accounts: `POST /api/v1/accounts/r_…/follow` records the follow in `outbound_follows` (migration 0076, one row per account and actor with its `follow_activity_id`, `state` `Requested` or `Accepted`, and the `reblogs`/`notify`/`languages` options) and sends `Follow` to the actor's inbox once; following again only updates the options. A suspended domain, one outside the allow list, a blocked actor, or a blocked domain answers 403. A signed `Accept` from the followed actor (naming our `Follow` id, or embedding a `Follow` of it by a local actor) makes it `Accepted`; a `Reject` deletes it; another actor's answer is ignored. `unfollow` deletes the row and sends `Undo(Follow)`. Accepted remote follows count in `following_count`, list in `/api/v1/accounts/:id/following` and the AP `following` collection, and show in the Relationship (`requested` until accepted). The home timeline merges the followed actors' public, unlisted, and followers-only notes (follow `languages[]`, blocks, mutes, domain blocks, suspended domains, and muted threads applied; silenced domains still shown to followers), and followers-only remote notes open for accepted followers. Remote notes now take their language from `contentMap`. The row id is the cursor and `actor_uri` can be re-pointed, so a `Move` can carry a follow over. Follow-ups: `notify` status notifications for remote posts, `followed_by` from `remote_follows`, severing follows when a domain is suspended later, `Undo(Follow)` when a local account is deleted, and `following=true` account search for remote accounts.

- Poll `Update(Question)` debounce, as Mastodon's `DistributePollUpdateWorker`: a vote (remote on a local poll, or local through `POST /api/v1/polls/:id/votes`) on a poll that shows its totals claims `polls.update_queued_at` (migration 0075, one `UPDATE ... WHERE update_queued_at IS NULL RETURNING id`) and only the claiming vote sends a `DistributePollUpdate { pollId }` job with `delaySeconds: 180` (`POLL_UPDATE_DELAY_SECONDS` in `src/poll-update.ts`); a failed send releases the claim. The job clears the claim first, so later votes queue a fresh job, then federates one `Update(Question)` with the counts as they are. Local votes sent no `Update` before; they do now, so remote audiences see them.

- Local polls federate as Mastodon polls: `noteDocument` serializes a note with a poll as a `Question` (`oneOf`/`anyOf` options with `replies.totalItems`, `endTime`, `closed` once expired, `votersCount` via the `toot:` context term; counts withheld while `hide_totals` is on) in the `Create`, the note document, the stored outbox `Create` and the edit `Update`. An inbox `Create` of a content-less `Note{name, inReplyTo: <local poll note>}` is a vote: counted in `remote_poll_votes` (migration 0073; single choice takes one option per actor, multiple choice one vote per option, expired polls, unknown options, repeats and followers-only polls from non-followers are ignored), never stored as a remote status and never a mention notification; counts and `voters_count` (now a real distinct-voter count for every poll) include remote votes, and the counted votes federate an `Update(Question)` to the note's audience (debounced, see below). Follow-ups: the outbox collection serves the `Create` as stored, so its poll counts are those at posting time; purge a deleted remote actor's poll votes, and decrement counts when a vote is retracted.

- Inbox account `Delete`: a remote actor deleting itself (signed with its cached key, object equal to its own URI, bare or embedded) purges its `remote_actors` row, which cascades to its statuses, follows, favourites and announces, plus its notifications and the blocks, mutes, endorsements and notes keyed by its URI. Another actor's URI is ignored, and a repeat from an already purged actor is a 202. The same batch also fails the queued `outbox_deliveries` to its inbox (state `Failed`/`Permanent`/410; a shared inbox stays while another cached actor uses it) and drops `status_mutes`, `conversation_reads` and `conversation_hides` rows keyed by its statuses. `updateOutboxTarget` only writes rows still `Queued`, so a delivery workflow that was mid-attempt or sleeping cannot revive a cancelled row and stops at its next `load` step. Before the purge `purgeRemoteActorAndAnnounce` (`src/remote-actor-purge.ts`) reads the actor's newest `PURGE_ANNOUNCED_ENTRY_LIMIT` (20) non-direct statuses and boosts and up to `PURGE_ANNOUNCED_FOLLOWER_LIMIT` (1000) local followers (the follows go with the purge, so a `FanOutHome` job could no longer find them), then queues `FanOutRemovedStatuses { accountIds, statusIds }` jobs of at most 20 x 20 that send each follower's `user` and list streams a `delete`. Older statuses and followers past the cap drop out on the next timeline fetch. Local boosts of its statuses go with them by cascade and their boosters' followers hear a `delete` (see below). Not done: `delete` events for the remote boosts of a deleted status (`remote_boosts` cascade), and thread marks for single remote `Delete`s (only a purge drops them)

- Voting on a remote poll: `POST /api/v1/polls/remote-<id>/votes` validates (visible, not ended, choices in range, one choice for a single-choice poll, one vote per account, author domain not suspended, blocked by the voter, or outside the allow list), stores the votes in `remote_poll_own_votes`, and federates one `Create(Note{name, inReplyTo, to: author})` per choice to the author's own inbox. The Poll entity carries `voted` and `own_votes` on every remote status render, and the votes are added to the displayed counts until the author's next changed `Update(Question)` tally replaces them. The vote Notes are not served at their `/users/:name/statuses/:id` URIs (Mastodon does not dereference them either).
- Remote polls, read-only: a remote `Question` (`oneOf` single, `anyOf` multiple choice, option counts, `endTime`/`closed`, `votersCount`) is stored in `remote_statuses.poll_json` and rendered as the Mastodon Poll entity (id `remote-<status id>`, also served by `GET /api/v1/polls/:id`); an author `Update(Question)` refreshes counts without setting `edited_at`. The author is remote, so nobody else is told.

- Inbox `Update`: a remote edit of a cached note (author-checked, `edited_at` rendered, newer edit wins, new mentions notified once) and a remote actor profile refresh. Edit history: each content-changing `Update` keeps the version it replaces in `remote_status_edits` (migration 0094), and `GET /api/v1/statuses/:id/history` renders them as StatusEdit entities, the original first and the current version last (a note edited before this change shows only its current version); `/source` answers 404 for a remote note and, now, for another account's local note. Local boosters of the edited note get an `update` notification; follow-up: the same for quotes once local quotes of remote statuses exist. Local polls send no `poll` notification at expiry either (only a `status.update` to the author's stream); Mastodon notifies the voters and the author.
